GigaBrain — Architecture Note · Master's Research

A Multi-Agent Model for Defining Software Requirements

Architecture draft — version 2

Abstract. This document describes the architecture of GigaBrain, an LLM-based agent model to support the definition of software requirements. The architecture organizes the agents into two councils: a deliberative council, in which the real Product Owner (PO) negotiates directly with a digital twin until they converge on a defined requirement; and a consultative council, responsible for holding the knowledge of each topic and mobilizing domain experts on demand. The consultative council is led by a manager agent, which consults a registry of experts and decides, for each question, whether an expert already exists or must be created — in which case the new agent builds its own knowledge file from the documents and the answers the PO provides, never from the source code or the web. A critic scores every proposed requirement against objective criteria without rewriting it, and sends back what does not pass; the PO has the final word, and approved requirements are saved, with versions, links and traceability, in a repository kept separately for each project. Figure 1 shows this architecture in detail.

1. Agent Roles

Table 1. Roles and responsibilities in the model.
Agent / resourceRole
Real POThe person who actually decides; asks questions, proposes changes and approves the final version of the requirement.
Digital TwinReplica of the real PO inside the system; debates with the human, asks the consultative council the right question and translates the answer into product language.
CriticScores each proposed requirement (ambiguity, completeness, verifiability, consistency with the saved ones) without an LLM by default; reports to the twin and sends back what fails. It informs, it never writes or decides.
Leader of the Consultative CouncilThe only agent present from the start; consults the expert registry, decides whether an expert already exists and creates a new one when the topic is new.
Domain ExpertsAgents created on demand, one per topic (payments, search, etc.), plus a quality expert that is always present; each keeps its own knowledge file and answers the leader.
Knowledge filesOne Markdown file per expert, fed by the documents and the answers the PO provides. No source code and no web research.
Requirements RepositoryStores the approved requirements (user story, EARS statement and Given/When/Then criteria) with versions, links and traceability. Each project has its own repository.

2. Example Flow: Payment Notification

  1. The real PO asks: "I want to add a notification to the payment".
  2. The digital twin passes the question to the leader of the consultative council.
  3. The leader consults the registry: is there already a payments expert?
  4. If there is, the leader asks it directly; if not, it creates a new expert and sends the question back to the PO through the twin, since the new expert only knows what the PO tells it.
  5. The expert answers the leader, which consolidates the knowledge and returns it to the digital twin — which resumes the conversation with the real PO.
  6. When the twin proposes a requirement, the critic scores it and reports what is ambiguous or missing; the twin revises and the PO approves it, saving it in the project's repository.
